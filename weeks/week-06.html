02 · System security

Understanding system hacking

System hacking describes attempts to gain or misuse access to an operating system, accounts, applications, or data. In an authorized security assessment, the goal is to understand how a system could be compromised and recommend controls that reduce the risk.

Common stages discussed in security assessments

StageAttacker objectiveDefensive focus
Credential attackObtain or guess account credentials.Strong authentication, MFA, rate limiting, secure password storage.
Privilege escalationObtain permissions beyond the initial account.Least privilege, patching, access reviews, secure configuration.
Application executionRun code or misuse legitimate tools.Application control, endpoint monitoring, restricted permissions.
ConcealmentMake malicious files or activity harder to notice.File integrity monitoring, centralized logs, endpoint detection.
PersistenceRetain access after a restart or session end.Startup and service monitoring, account reviews, trusted boot.
Anti-forensicsInterfere with investigation or evidence.Protected audit logs, time synchronization, evidence preservation.
Professional practice: The stages above are a learning framework, not a checklist for compromising systems. In this course, practical work focuses on recognizing indicators, verifying controls, and documenting findings without establishing unauthorized access or hiding activity.
03 · Credential security

Password attacks and password protection

Passwords are a common target because they protect access to accounts, devices, and services. A password audit evaluates whether password policies and storage mechanisms resist guessing and offline recovery attempts.

TechniqueConceptDefensive control
Dictionary guessingTests likely words or commonly used passwords.Block common passwords; use long unique passphrases and MFA.
Brute-force guessingSystematically tries combinations.Rate limiting, lockout protections, MFA, and monitoring.
Hybrid guessingCombines word candidates with predictable variations.Use unpredictable, unique passwords rather than simple substitutions.
Password sprayingTries a small set of common passwords across multiple accounts.Authentication monitoring, MFA, smart throttling, and banned-password lists.
Credential stuffingReuses credentials exposed in unrelated breaches.Unique passwords, MFA, breach monitoring, and secure recovery processes.
Rainbow-table lookupUses precomputed hash lookup data against unsalted hashes.Unique salts and modern, deliberately slow password-hashing algorithms.

Hashes and password storage

A cryptographic hash maps input data to a fixed-length digest. Password systems should not store plaintext passwords or rely on fast general-purpose hashes alone. They should use password-hashing schemes designed to resist guessing, with a unique salt for each password.

Algorithm / formatSecurity context
LMLegacy Windows hash format; obsolete and insecure.
NTLMLegacy Windows authentication hash; requires careful protection and modern alternatives where possible.
MD5 / SHA-1Not suitable for password storage; both are considered unsuitable for modern security use.
SHA-256 / SHA-512General-purpose cryptographic hashes; fast, so not ideal alone for password storage.
bcrypt / scrypt / Argon2idPassword-hashing functions designed to make guessing more expensive; use appropriately configured parameters.

Credential protection checklist

  • Require long, unique passwords and use a reputable password manager.
  • Enable multifactor authentication, especially for privileged accounts.
  • Store passwords using a modern password-hashing function with unique salts.
  • Protect password reset and account recovery workflows.
  • Monitor unusual login patterns and repeated failures.
  • Remove stale accounts and rotate credentials after suspected compromise.
04 · Access control

Privilege escalation

Privilege escalation occurs when a user or process obtains permissions beyond those intended by the system's access-control design.

Risk areaExample weaknessDefensive measure
Operating systemUnpatched kernel or system component.Supported versions, timely patching, controlled maintenance.
File permissionsSensitive files or executables are writable by untrusted users.Least privilege and regular permission reviews.
ServicesA privileged service uses unsafe files or configuration.Dedicated service accounts, protected paths, secure service configuration.
Scheduled tasksA privileged task references files that ordinary users can change.Restrict task modification and verify ownership and permissions.
Stored credentialsSecrets are left in scripts, configuration files, or logs.Use a secrets manager and restrict access to sensitive files.
Administrative delegationBroad or unnecessary sudo / administrator rights.Use narrowly scoped permissions and periodic access reviews.

Linux commands for authorized, read-only inspection

# Current account and group membership
whoami
id

# Operating system and kernel information
uname -a
cat /etc/os-release

# Review the current account's permitted sudo commands
sudo -l

# Display permissions on selected system paths
ls -ld /etc /etc/cron.d /usr/local/bin

These commands help document the current account and configuration. Do not modify permissions, replace binaries, alter scheduled tasks, or attempt to exploit a weakness during this inspection exercise.

05 · File integrity

Hidden files and suspicious changes

Operating systems use hidden files for ordinary configuration and application data. On Linux, filenames beginning with a dot are hidden by default in many file browsers. Hidden does not mean malicious; investigate context, ownership, permissions, timestamps, and file integrity before drawing conclusions.

# List ordinary and hidden entries in your own lab home directory
ls -la ~

# Display file type and permissions for a selected file
file ~/example-file
stat ~/example-file

# Generate a SHA-256 checksum for a file you own
sha256sum ~/example-file

File integrity monitoring compares trusted checksums or metadata over time to help identify unexpected changes. A changed checksum is an investigation lead, not proof of malicious activity.

06 · Digital forensics

Covering tracks and anti-forensics awareness

Attackers may attempt to delete, alter, or avoid generating logs to make an incident harder to investigate. This is commonly described as covering tracks or anti-forensics. Security professionals study these behaviors to recognize gaps and preserve reliable evidence.

Defensive logging practices

  • Forward important logs to a separate, access-controlled logging platform.
  • Restrict who can change or delete audit records.
  • Synchronize system clocks with trusted time sources.
  • Retain logs according to legal, operational, and organizational requirements.
  • Alert on unexpected changes to audit settings, logging services, or retention policies.
  • Preserve original evidence and document every investigative action.
Evidence handling: Never delete or alter logs as part of this lesson. If you suspect a compromise, preserve relevant records, record timestamps and system details, and follow your incident-response process.
07 · Threat detection

Rootkits, backdoors, and persistence

A rootkit is a collection of techniques or components intended to conceal malicious activity or maintain privileged access. A backdoor is an access mechanism that bypasses normal authentication or security controls. Persistence refers to techniques that allow unwanted access or execution to survive events such as logoff or restart.

Potential indicators to investigate

  • Unexpected services, startup entries, scheduled tasks, or user accounts.
  • Changes to system binaries or security configuration without an approved change record.
  • Unusual privileged processes or unexplained network connections.
  • Security tools unexpectedly disabled or audit settings modified.
  • File integrity alerts involving critical operating-system locations.

Defensive response

  1. Preserve relevant logs and record the time and source of the alert.
  2. Compare the affected system with a trusted baseline.
  3. Use reputable endpoint security and integrity-monitoring tools.
  4. Isolate a suspected compromised machine according to incident-response policy.
  5. Rebuild from trusted media when integrity cannot be established, then rotate affected credentials.
08 · Information hiding

Steganography

Steganography is the practice of concealing information inside an ordinary-looking carrier, such as an image, audio file, or document. It differs from encryption: encryption protects the meaning of data, while steganography attempts to conceal the existence of the data.

ConceptPurpose
EncryptionMakes information unreadable without the required key.
SteganographyHides the presence of a message within another file or medium.
Digital watermarkingEmbeds identifying or ownership information in media.

For defensive investigation, compare files with trusted originals, examine metadata, review unexpected file-size changes, and use approved forensic tools. No hidden-data extraction from third-party files is part of this practical lesson.

09 · Practical lab 6

System security audit and credential hygiene

Objectives

  • Inspect account identity and permissions on a system you control.
  • Review password-storage principles using synthetic training data.
  • Identify suspicious permission and persistence indicators without changing the system.
  • Practice evidence preservation and write defensive recommendations.
Lab scope: Use your own Kali VM or another Linux test VM. Do not extract password databases, use real users' password hashes, attempt logins with recovered credentials, exploit vulnerabilities, modify startup entries, or delete logs. The exercises below are read-only.

Step 1: Record system identity

whoami
id
hostname
uname -a
cat /etc/os-release

Record the operating system, current user, groups, and kernel information. Avoid including personal information in screenshots submitted publicly.

Step 2: Review account and permission controls

# Review your own home directory permissions
ls -ld ~

# Inspect selected configuration directory permissions
ls -ld /etc /etc/ssh

# Review the current account's administrative permissions
sudo -l

Do not read or copy /etc/shadow or other users' credential stores. Document any unexpectedly broad permissions and explain how least privilege should be applied.

Step 3: Learn password hashing with synthetic data

Use a made-up training password and a generated sample hash from an instructor-approved password-hashing demonstration. Do not use real account hashes or passwords. In your notes, explain why unique salts and slow password-hashing functions reduce the effectiveness of precomputed and high-speed guessing attacks.

Step 4: Review integrity and persistence indicators

# List startup-related systemd services (read-only)
systemctl list-unit-files --type=service

# Review recent system log entries (read-only)
journalctl -n 30 --no-pager

# Inspect your own home directory, including hidden entries
ls -la ~

Identify entries you cannot explain and describe how you would verify them against a trusted baseline. Do not disable services or alter audit records.

Step 5: Prepare a defensive audit report

Document the environment, commands used, observations, evidence, risk, and recommended controls. Clearly distinguish confirmed configuration issues from items that require further investigation.

Expected outcomes

  • System and account inventory for the test VM.
  • Read-only permission and service review.
  • Explanation of secure password storage and hash auditing concepts.
  • Examples of persistence and anti-forensics indicators.
  • A concise defensive system-audit report.
10 · Assessment

Assignment 6

Part A: System security audit (60 points)

Perform a read-only security review of a Linux VM you own or are explicitly authorized to assess.

  1. Document the operating system, kernel, current user, and group membership.
  2. Review selected directory permissions and the current account's administrative privileges.
  3. Explain how secure password storage works. Use synthetic examples only; do not collect or crack real users' hashes.
  4. Identify at least three security controls that help prevent privilege escalation.
  5. Describe two indicators of suspicious persistence and how a defender could investigate them without altering evidence.

Part B: Research and analysis (40 points)

Research the following five Linux privilege-escalation risk categories:

  1. Unpatched kernel or operating-system components.
  2. Unsafe SUID/SGID configuration.
  3. Writable sensitive files or directories.
  4. Insecure scheduled-task configuration.
  5. Overly broad sudo permissions.

For each category, explain what the weakness means, how an administrator can identify it safely, the potential impact, and practical prevention measures. Do not provide or demonstrate exploitation steps.

Submission format: A professional technical document with screenshots of your own lab, read-only commands, observations, risk analysis, and remediation recommendations. Do not include passwords, private keys, credential hashes, or unrelated personal data.
